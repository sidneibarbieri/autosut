# Proposal and Admission Boundary

## Purpose

This document fixes the trust boundary for model-assisted reconstruction. It prevents a planning proposal from becoming an execution claim merely because it is syntactically compatible with a laboratory host.

Let `G` be a STICKS-derived causal plan, `S` a declared SUT composition, `A` a versioned finite action-contract catalog, and `O` an independently declared effect-oracle catalog. A model may propose a candidate `p`, but it cannot alter `G`, `S`, `A`, or `O`. Execution is permitted only for an action contract `a` for which the deterministic verifier accepts `V(G, S, a, O)`. A proposal without such a contract remains `not_run`.

## Decision Record

| Option | Decision | Reason |
|---|---|---|
| D1: unrestricted model agent | Rejected | An open-ended proposer that writes, dispatches, and repairs commands combines authority over proposal, decision, execution, and judgment. Resource checks do not prove shell semantics, technique fidelity, safety, or an independently observed effect. |
| D2: fixed catalog and deterministic binding | Baseline and trusted core | A versioned action catalog, typed SUT bindings, and deterministic search are replayable. By itself, D2 leaves campaign-specific candidate completion and selection as an offline human bottleneck. |
| D3: bounded proposal with deterministic admission | Target runtime architecture | D3 retains D2's finite contracts, but an untrusted proposer may suggest only candidates that exactly match a predeclared contract. The verifier fails closed; model output cannot create a new command interface, effect, binding schema, fidelity tier, or oracle. |

The current artifact implements the planning and admission boundary of D3: it
binds untrusted proposals to a declared plan and SUT context, screens explicit
requirements, retains hashes and abstentions, and records `not_run` without
executing model output. It does not yet publish a general catalog of reviewed
action implementations paired with independent effect oracles. It therefore
does not support a broad campaign-execution claim.

## Required Contract Fields

Each executable catalog entry must be immutable and contain:

- a stable contract identifier and content hash;
- one ATT&CK technique identifier and an explicit laboratory scope;
- a reviewed action implementation or action-template reference;
- typed input bindings, preconditions, postconditions, and causal dependencies in `G`;
- a SUT capability contract that names the required services, identities, artifacts, and topology;
- an effect predicate defined independently of any model response;
- provenance, fidelity tier, safety boundary, and an abstention code.

The effect predicate is evaluated before and after dispatch. It must be tied to the registered contract, not generated by the proposer, and must record enough evidence for a reviewer to replay the check. A successful predicate establishes only the contract's declared laboratory effect; it does not by itself establish historical fidelity.

## State Model

The pipeline emits one of these states for each plan step:

1. `proposed`: a model or other proposer supplied a candidate.
2. `resource_compatible`: the candidate's declared footprint is compatible with `S`.
3. `contract_admitted`: a registered contract satisfies the deterministic verifier.
4. `executed`: the registered action ran in the declared isolated substrate.
5. `effect_observed`: the independent contract predicate changed as expected.
6. `abstained`: no admissible contract or substrate exists; the reason is retained.

Only states 3--5 are execution-layer evidence. State 2 is a planning result, not an execution success rate or a measure of ATT&CK fidelity.

## Human Role

D3 removes discretionary **online** intervention inside the declared catalog
and SUT scope. It cannot honestly erase offline scientific work: someone must
author and validate contracts, define safety boundaries, build independent
oracles, and decide whether a source CTI claim supports a laboratory
realization. Those inputs are versioned evidence, not silent manual curation.

## Evaluation Needed Before a Broader Claim

A broader automation claim requires a preregistered corpus, fixed model and retry policy, paired baselines, execution traces, contract-level oracle outcomes, cost and human-effort measurements, and an independent-host reproduction. Unsupported platforms, techniques, topology, or contracts must be counted as abstentions rather than repaired during collection.
